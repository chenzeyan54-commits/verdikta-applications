# BountyEscrow v0.5.0 cutover runbook (2026-09-12)

Breaking contract revision: new address per network, new ABI everywhere. Do **testnet first**, verify, then mainnet.
Everything below assumes the main tree at `/root/verdikta/applications/example-bounty-program`.

## What is already in place (committed or in the working tree)
- Contract + tests: `onchain/` (212 tests passing). Deploy from here.
- Docs describing the new system: `README.md`, `DEVELOPER-GUIDE.md`, `CLAUDE.md`, `server/routes/agentRoutes.js` (served docs only), `client/src/pages/{Agents,Blockchain,CreateBounty}.jsx` (doc copy only).
- The off-chain code migration as a patch: `deploy/cutover-2026-09-12.patch` (21 files, server + client + scripts). It was verified with `git apply --check` against this tree, `node --check` on every .js, `esbuild` on every .jsx, and the server's jest suite (132 tests). It deliberately excludes `Agents.jsx` and `Blockchain.jsx` (their patch-side edits were doc-only and this tree already has newer doc text).

## Step 0 — before touching anything
- Close out the OLD contract's business: finalize/force-fail every pending submission and close every expired bounty on the old address. After the flip the server tracks only the new contract (sync is keyed per network, not per address). `GET /api/jobs/mine/action-required?creator=0x…` and `GET /api/jobs/admin/expired` list what is left.
- Commit the working tree (contract, tests, docs) so the patch applies onto a known state. If anything else lands first, re-check: `git apply --check deploy/cutover-2026-09-12.patch`.

## Step 1 — deploy the contract (per network)
```
cd onchain
npm test                      # expect 231 passing
npm run deploy:sepolia        # or: npm run deploy:base
```
The script reads `VERDIKTA_AGGREGATOR_BASE[_SEPOLIA]` from `onchain/.env`, prints the new address, saves `onchain/deployments/<chainId>-<network>.json`, and verifies on Basescan when `BASESCAN_API_KEY` is set. Note the **address** and the **deployment block** (from the tx receipt / Basescan).

The escrow's constructor also creates `BountyEscrowLens` (its read-only views, split out for bytecode size; served at the escrow address via the fallback). The script prints and records its address and verifies it too; if lens verification fails, run `npx hardhat run deploy/verify.js --network <net> <escrow>` later, or the printed `npx hardhat verify --contract contracts/BountyEscrowLens.sol:BountyEscrowLens …` line. Nothing off-chain needs the lens address: the server and client ABIs are hand-written fragment lists that already name the views.

Also in this contract revision (2026-09-12, pre-deploy review fix): payout priority is now by submission index among IN-FLIGHT submissions on EVERY bounty (copy protection against a duplicated public work CID). `finalizeSubmission` may revert `earlier submission pending - retry after it resolves` on non-windowed bounties too — the patched client already treats that string as retry-later generically (`isRetryableRevert`), and the server's finalize path has no windowed-only gating on it. No ABI change. The 128 prepared-submission cap now applies to WINDOWED bounties only; non-windowed bounties are uncapped on prepares and instead cap concurrent evaluations at `MAX_ACTIVE_EVALUATIONS = 256` (new start-time revert `evaluation slots full - retry later` — a retry, not a failure; the migration patch maps it in the client: friendly message, `isRetryableRevert()` true, retry-later handling on the Submit and Bounty pages). New reads: `pendingSubmissionIds(bountyId)`, `getSubmissionsPage(bountyId, start, count)`; `activeEvaluations` is now a function (same signature). Off-chain follow-up (not a blocker): the sync service / jobs.json store every prepared submission per bounty; a junk-flooded non-windowed bounty can now hold thousands — add a per-bounty bound or skip never-started prepares from other hunters, and switch bulk reads to `getSubmissionsPage`. Only a consumer of the compiled artifact ABI would — the export in `onchain/frontend/src/abi/BountyEscrow.json` is now the merged (escrow + lens) ABI.

## Step 2 — stop services
```
server/stopServer.sh
client/stopClient.sh          # the build-watch would otherwise rebuild mid-patch
```

## Step 3 — apply the code migration
```
git apply deploy/cutover-2026-09-12.patch
```

## Step 4 — configuration
- `server/.env`: `BOUNTY_ESCROW_ADDRESS_BASE_SEPOLIA=` / `BOUNTY_ESCROW_ADDRESS_BASE=` → new address.
- `client/.env`: `VITE_BOUNTY_ESCROW_ADDRESS_BASE_SEPOLIA=` / `VITE_BOUNTY_ESCROW_ADDRESS_BASE=` → new address.
- `server/config.js` → `deploymentBlocks['base-sepolia' | 'base']` → new deployment block (the sync bootstrap replays from here; leaving the old block makes it scan old-address logs and skip them).

## Step 5 — data
Bounty IDs restart at 0 on the new contract and `jobId == on-chain bountyId`, so the old `jobs.json` would collide.
```
cd server/data/<network>
cp jobs.json jobs.json.pre-v050-$(date +%s)      # keep the history
rm jobs.json                                      # fresh file; sync bootstraps from deploymentBlock
```
(`syncState.lastSyncedBlock` lives inside `jobs.json`, so removing the file resets it too.)

## Step 6 — start and check
```
server/startServer.sh
client/startClient.sh          # build-watch; rebuilds the static site
curl -s localhost:5005/health
```
- `/analytics` on the site shows the live escrow address from runtime config — it must be the new one.
- `POST /api/jobs/sync/now` then `GET /api/jobs` → empty (or the first new bounty).

## Step 7 — smoke test (testnet)
1. Create a bounty on the site (leave oracle settings at defaults). `GET /api/jobs/:id` → `oracleSettings {maxOracleFee, alpha, estimatedBaseCost, maxFeeBasedScaling}`; the on-chain tx must be the struct `createBounty`.
2. `GET /api/jobs/:id/oracle-check` → `available:true`, counts for class 128/131, no scary warnings.
3. Validate on the Home card shows the oracle-check block.
4. Submit work → `/submit/bundle/complete` returns `parsed.ethMaxBudget` ≈ 0.00024 ETH (not 96 wei); `/start`'s `transaction.value` equals `requiredPrepay(bountyId)` on the escrow (read it with `cast call` or the Blockchain page) → start → wait → finalize. `GET /api/jobs/:id/submissions` shows `paidWinner:true` for the winner (from the `paid` flag) and `funder` set.
5. Force-fail path: `/timeout` on a fresh pending submission returns `canTimeout:false` with `error: "Evaluation not settled"` and a hint; after the oracle responds it returns `canFinalize:true`.
6. If any resolving tx shows `RefundDeferred` in the logs, the submission card offers "Recover oracle prepay"; `recoverLeftoverEth` must succeed.
7. Agent views: `GET /api/jobs/:id/onchain-status` returns `requiredPrepay` and `prepareCutoff`; `GET /api/jobs/:id/submissions/:subId/diagnose` returns `nextAction`; `GET /api/jobs/withdrawable/<addr>` answers; `cast call <escrow> "nextAction(uint256,uint256)(string)" <b> <s>` matches the diagnose value.
8. Close an expired test bounty.

## Step 8 — mainnet
Repeat Steps 1–7 (smoke test 1–8) for `base`.

## Step 9 — cleanup
```
cd /root/verdikta/applications
git worktree remove example-bounty-program-cutover --force
sed -i '/example-bounty-program-cutover/d' .git/info/exclude
```
Commit the applied migration (the patch file can stay as a record or be deleted).

## Rollback (before Step 7 passes)
- Restore old addresses + `deploymentBlocks`, restore `jobs.json` from the backup, `git apply -R deploy/cutover-2026-09-12.patch`, restart. The old contract is untouched throughout.

## Known follow-ups (not blockers)
- Website has no generic "withdraw()" claim button yet; a contract-wallet recipient whose payout was deferred (`PaymentDeferred`) must call `withdraw()` directly.
- `/admin/stuck` still uses a 10-minute age as a listing filter (the gate itself is aggregator-based).
- Scripts under `server/scripts/` compute deadlines from `Date.now()` independently of the API (pre-existing).
