# BountyEscrow v0.5.0 cutover runbook (2026-09-12)

Breaking contract revision: new address per network, new ABI everywhere. Do **testnet first**, verify, then mainnet.
Everything below assumes the main tree at `/root/verdikta/applications/example-bounty-program`.

## What is already in place (committed or in the working tree)
- Contract + tests: `onchain/` (212 tests passing). Deploy from here.
- Docs describing the new system: `README.md`, `DEVELOPER-GUIDE.md`, `CLAUDE.md`, `server/routes/agentRoutes.js` (served docs only), `client/src/pages/{Agents,Blockchain,CreateBounty}.jsx` (doc copy only).
- The off-chain code migration as a patch: `deploy/cutover-2026-09-12.patch` (21 files, server + client + scripts). It was verified with `git apply --check` against this tree, `node --check` on every .js, `esbuild` on every .jsx, and the server's jest suite (132 tests). It deliberately excludes `Agents.jsx` and `Blockchain.jsx` (their patch-side edits were doc-only and this tree already has newer doc text).

## Step 0 — before touching anything
- Close out the OLD contract's business: finalize/force-fail every pending submission and close every expired bounty on the old address. After the flip the server tracks only the new contract (sync is keyed per network, not per address). `GET /api/jobs/mine/action-required?creator=0x…` and `GET /api/jobs/admin/expired` list what is left.
- Commit the working tree (contract, tests, docs) so the patch applies onto a known state. If anything else lands first, re-check: `git apply --check deploy/cutover-2026-09-12.patch`.

## Step 1 — deploy the contract (per network)
```
cd onchain
npm test                      # expect 246 passing
npm run deploy:sepolia        # or: npm run deploy:base
```
The script reads `VERDIKTA_AGGREGATOR_BASE[_SEPOLIA]` from `onchain/.env`, prints the new address, saves `onchain/deployments/<chainId>-<network>.json`, and verifies on Basescan when `BASESCAN_API_KEY` is set. Note the **address** and the **deployment block** (from the tx receipt / Basescan).

The escrow's constructor also creates `BountyEscrowLens` (its read-only views, split out for bytecode size; served at the escrow address via the fallback). The script prints and records its address and verifies it too, and likewise the `EvaluationWallet` implementation (`walletImplementation()`, constructor args `(escrow, aggregator)`) that every submission wallet is an EIP-1167 clone of — verify it so Basescan labels the clones; if lens verification fails, run `ESCROW=<escrow> npx hardhat run deploy/verify.js --network <net>` later (hardhat does not forward positional args), or the printed `npx hardhat verify --contract contracts/BountyEscrowLens.sol:BountyEscrowLens …` line. Nothing off-chain needs the lens address: the server and client ABIs are hand-written fragment lists that already name the views.

Also in this contract revision (2026-09-12, pre-deploy review fix): payout priority is now by submission index among IN-FLIGHT submissions on EVERY bounty (copy protection against a duplicated public work CID). `finalizeSubmission` may revert `earlier submission pending - retry after it resolves` on non-windowed bounties too — the patched client already treats that string as retry-later generically (`isRetryableRevert`), and the server's finalize path has no windowed-only gating on it. No ABI change. Gas work (Tier A, same day): wallet clones + narrowed struct field types — `prepareSubmission` 650k → 282k gas, create 384k → 323k, finalize 315k → 262k with a 3-CID justification, escrow 18.1 KB; new getter `walletImplementation()`; `EvaluationWallet.hunter()` removed (nothing off-chain read it). The narrowed types are decoder-compatible: every integer still encodes as one 32-byte word, so the `uint256`-declared fragments in the server/client/scripts and in this patch decode unchanged. TIER B (same day): `Submission.justificationCids` is REMOVED from the struct (finalize with a 3-CID justification 262k → 123k gas; start 443k → 424k); every `getSubmission`/`getSubmissions`/`getSubmissionsPage` tuple fragment in this patch and in `client/src/pages/Blockchain.jsx` drops the field, the two chain wrappers (`server/utils/contractService.js`, `client/src/services/contractService.js`) return an empty string for it, and the local job data keeps getting the CIDs from the `SubmissionFinalized` event / aggregator via the sync service (unchanged). Patch regenerated. Also (review fixes): `nextAction` gained AWAIT_SLOT and AWAIT_EARLIER and now returns DEAD when an in-flight sibling already passes, FINALIZE vs FORCE_FAIL past the timeout follows the aggregator's late-reveal state; `isAcceptingSubmissions` honours the windowed cutoff and the 128 cap; revert strings changed: `closeExpiredBounty` says `bounty not open` (was `not open`), start says `already started or resolved` (was `not prepared`), finalize on a settled-no-result round says `no oracle result - use failTimedOutSubmission` (`Verdikta not ready` = no answer yet). The patched client maps all of these (plus the previously unmapped `not resolved`, `never started`, `nothing to recover`, `withdraw failed`, `nothing to withdraw`, `unknown function`, `self only`, `reentrant`) and routes `no oracle result` to the force-fail path. The 128 prepared-submission cap now applies to WINDOWED bounties only; non-windowed bounties are uncapped on prepares and instead cap concurrent evaluations at `MAX_ACTIVE_EVALUATIONS = 256` (new start-time revert `evaluation slots full - retry later` — a retry, not a failure; the migration patch maps it in the client: friendly message, `isRetryableRevert()` true, retry-later handling on the Submit and Bounty pages). New reads: `pendingSubmissionIds(bountyId)`, `getSubmissionsPage(bountyId, start, count)`; `activeEvaluations` is now a function (same signature). Off-chain follow-up (not a blocker): the sync service / jobs.json store every prepared submission per bounty; a junk-flooded non-windowed bounty can now hold thousands — add a per-bounty bound or skip never-started prepares from other hunters, and switch bulk reads to `getSubmissionsPage`. Only a consumer of the compiled artifact ABI would — the export in `onchain/frontend/src/abi/BountyEscrow.json` is now the merged (escrow + lens) ABI.

## Step 7 — smoke test (testnet)
1. Create a bounty on the site (leave oracle settings at defaults). `GET /api/jobs/:id` → `oracleSettings {maxOracleFee, alpha, estimatedBaseCost, maxFeeBasedScaling}`; the on-chain tx must be the struct `createBounty`.
2. `GET /api/jobs/:id/oracle-check` → `available:true`, counts for class 128/131, no scary warnings.
3. Validate on the Home card shows the oracle-check block.
4. Submit work → `/submit/bundle/complete` returns `parsed.ethMaxBudget` ≈ 0.00024 ETH (not 96 wei); `/start`'s `transaction.value` equals `requiredPrepay(bountyId)` on the escrow (read it with `cast call` or the Blockchain page) → start → wait → finalize. `GET /api/jobs/:id/submissions` shows `paidWinner:true` for the winner (from the `paid` flag) and `funder` set.
5. Force-fail path: `/timeout` on a fresh pending submission returns `canTimeout:false` with `error: "Evaluation not settled"` and a hint; after the oracle responds it returns `canFinalize:true`.
6. If any resolving tx shows `RefundDeferred` in the logs, the submission card offers "Recover oracle prepay"; `recoverLeftoverEth` must succeed.
7. Agent views: `GET /api/jobs/:id/onchain-status` returns `requiredPrepay` and `prepareCutoff`; `GET /api/jobs/:id/submissions/:subId/diagnose` returns `nextAction`; `GET /api/jobs/withdrawable/<addr>` answers; `cast call <escrow> "nextAction(uint256,uint256)(string)" <b> <s>` matches the diagnose value.
8. Close an expired test bounty.

## Findings from the 2026-09-12 testnet run (not blockers)
- Lagging RPC reads: on Infura Base Sepolia an `eth_call` issued right after a receipt can hit a node one or two blocks behind and return stale/empty data. Seen three times: the deploy script's post-deploy `lens()` read (now retried), `POST /submissions/confirm` immediately after the prepare receipt (server reverted "bad submissionId"; a retry 5 s later succeeded — the confirm endpoint should retry `getSubmission` a few times when the caller supplies a fresh txHash), and every read in the second after force-fail/close. Wait a block before reading back, or read via the receipt's events.
- `POST /finalize` on a round that is settled/timed out with no result answers the generic `Evaluation not ready` / "wait" hint; `/timeout` already answers `canTimeout:true`. The hint should point at `/timeout` when `nextAction` is `FORCE_FAIL`.
- The testnet oracle is thinly served right now: the first round got 2 of 6 commits and timed out; force-fail refunded 0.00012 ETH (prepay minus the 6 dispatched base fees), no `RefundDeferred`. A live start costs ~3.0M gas against the real aggregator (the API's 4M gas limit is right; do not lower it).
- `GET /jobs/:id` only carries `oracleSettings` for jobs created by the patched server; a job created by the old code before the restart lacks it until the sync's heal pass fills it from chain.
